# 错误、版本、变更集与快照

## 统一错误模型

可预期失败使用 `ApplicationError`，字段含义固定：

- `code`：稳定机器码，格式为 `<module>.<reason>`，例如 `manuscript.version_conflict`。
- `kind`：跨模块错误类别。
- `message`：可安全展示的中文说明，不包含堆栈、SQL、提示词或密钥。
- `retryable`：调用方在输入不变时是否可以安全重试。
- `details`：经过白名单筛选的结构化上下文。
- `causeId`：关联服务端日志和追踪的标识，不暴露内部异常。

类别到 HTTP 的默认映射为：`validation` 400、`unauthorized` 401、`forbidden` 403、`not_found` 404、`conflict` 409、`unavailable` 503、`internal` 500。领域层只产生领域含义，不引用 HTTP；presentation 层负责映射状态码。可预期分支返回 `Result<T>`，意外基础设施异常在边界转成 `internal` 或 `unavailable` 并记录原始原因。

只有 `retryable: true` 的冲突、暂时不可用或幂等后台操作允许自动重试。校验失败、权限失败和未知写入结果不得盲目重试。

## 聚合版本策略

- 新聚合持久化后的版本为 `1`，未持久化状态可视为 `0`。
- 每个写命令携带调用方最后读取的 `expectedVersion`。
- 事务以聚合标识和版本作为更新条件；不匹配时不写入任何状态，返回 `conflict`。
- 一次产生有效状态变化的命令将目标聚合版本恰好增加 `1`；语义无变化的幂等命令不增加版本。
- 多聚合用例仍分别维护聚合版本，并在一个应用事务内提交；项目级版本只表达项目快照变化，不能替代各聚合并发检查。
- 事件信封中的版本是事实发生后的版本，变更集保存命令前后的版本。

迁移期间，现有 `Project.revision`、`Chapter.contentRevision` 和内容哈希继续有效。新聚合版本只有在对应用例完整切换后才成为该用例的权威并发令牌。

## 变更集策略

一次成功、用户可感知的写命令生成一个不可变 `ChangeSet`。它记录项目、基础项目版本、目标项目版本、操作者、时间和一组 `AtomicChange`。每个原子变化包含目标聚合的提交后版本、操作类型、领域路径以及必要的前后值。

`AtomicChange` 使用判别联合表达合法形态：`create` 只有 `after`，`update` 同时具有 `before` 与 `after`，`delete` 只有 `before`。

变更集与聚合状态、领域事件在同一事务中提交。大段正文只记录可验证引用、内容哈希或受控差异，避免在多个记录中无限复制。敏感数据在进入变更集前按字段策略脱敏。

撤销不是删除历史或降低版本，而是读取目标变更集、重新校验当前状态，再通过目标模块公开命令生成一个新的反向变更集。无法安全反演时返回冲突并要求人工处理。跨模块变更由 application 编排，各模块仍校验自己的不变量。

## 快照策略

`AggregateSnapshot` 保存聚合标识、聚合版本、完整状态、内容哈希、捕获时间和可选变更集标识。快照是可丢弃的恢复加速器，权威事实仍是已提交状态与审计历史。

快照在明确边界生成，例如累计达到变更阈值、章节发布或导出前，不为每次输入事件创建。恢复时选择不高于目标版本的最新快照，验证标识、版本和哈希后再应用后续变更；校验失败则退回更早快照或从权威状态重建。

快照格式变化通过独立 schema 版本迁移。创建新快照前必须先提交业务事务；后台快照失败只影响性能，不影响已完成写入。保留和清理策略必须确保仍可从保留的快照与后续历史恢复到受支持的审计范围。
